원문에는 `10s^2x`가 있었는데, 뒤의 `x`를 뺀 `10s^2`가 답변 검증을 통과했습니다. 문서 ID와 인용문은 맞았습니다. 숫자와 단위를 확인하는 코드도 있었습니다. 다만 정규식이 지수의 앞부분만 읽고 남은 문자를 놓치고 있었습니다.

실제 모델의 응답을 평가한 사례는 아닙니다. 생성기 대역으로 답변을 넣는 테스트에서 재현한 오류입니다. 그래도 이 문제는 FieldMemory AI를 만들면서 다뤄 온 질문을 잘 보여 줍니다. 문서를 찾고 출처를 붙인 뒤에도, 그 답변을 받아들일 조건을 계속 확인해야 했습니다.

FieldMemory AI는 팀의 매뉴얼, 업무 가이드, 장애 기록과 경험 메모를 등록하고, 질문에 맞는 근거와 원문을 함께 보여 주는 로컬 웹앱입니다. [앞선 설계 글](https://beckspeca.github.io/blog/fieldmemory-ai-design/)에서는 만들려는 구조를 정리했습니다. 이번에는 2026년 9월 27일부터 10월 7일까지 실제로 구현하고 고친 과정을 돌아보겠습니다.

시연과 평가에는 가상 제조팀의 합성 자료를 사용했습니다. 현업에서 도입 효과를 측정한 프로젝트는 아니며, 현재 단계는 로컬 MVP와 검색 평가입니다.

## 문서에서 답변까지의 전체 흐름

앱의 전체 흐름을 한 장으로 정리했습니다. 왼쪽은 자료를 등록하고 검토하는 과정이고, 오른쪽은 사용자의 질문에 맞는 근거를 찾는 과정입니다. 준비한 색인과 검색 결과가 만나면 답변 생성과 검증으로 이어집니다.

![FieldMemory AI 전체 워크플로우. 문서 업로드·추출·보관·승인·색인에서 질문 검색과 최대 5개 근거 선택, 답변 생성·인용 검증·원문 확인으로 이어진다. 선택 기능과 근거 부족·연결 오류·자료 변경 시의 보류 경로, 별도 평가 흐름도 함께 표시했다.](/images/fieldmemory-ai/fieldmemory-workflow.svg)

*2026년 10월 8일 로컬 최신 구현을 기준으로 그린 흐름입니다. 점선 박스는 기본값이 꺼진 선택 기능이며, 켜지 않으면 해당 단계를 건너뜁니다. 최근 수정 중 일부는 기본 브랜치에 통합하기 전입니다. [원본 그림 크게 보기](/images/fieldmemory-ai/fieldmemory-workflow.svg)*

기본 경로는 **문서 등록 → 사람의 검토·승인 → 의미 검색 → 근거 선택 → 원문 확인**입니다. LLM을 연결하지 않아도 찾은 원문을 읽을 수 있습니다. 답변 생성을 선택하면 확인하고 저장한 연결만 사용하며, 인용과 자료 상태를 검사한 뒤 결과를 보여 줍니다. 근거가 부족하거나 검증에 실패하면 답변을 보류하거나 원문 근거로 돌아갑니다.

질문 요건 추출·근거 충분성 확인과 Jev의 재정렬·주장 검증은 선택 경로입니다. 이 기능을 구현한 사실과 실제 답변 품질이 좋아졌다는 판단은 별개입니다. 평가도 일반 검색과 분리해, 정답이 검색 자료에 섞이지 않도록 했습니다.

## 기획에서 로컬 MVP까지

시작할 때 가장 먼저 정리한 것은 제품의 범위였습니다. 내부 문서 검색, 경험 인터뷰, 선임의 판단을 모사하는 챗봇을 모두 한 번에 구현하기에는 확인해야 할 문제가 많았습니다. 첫 제품은 문서 등록부터 검토, 검색, 답변과 원문 확인까지 이어지는 흐름으로 잡았습니다. 경험 인터뷰는 후속 범위로 남겼습니다.

같은 저장소에 있던 이전 센서 분석 프로젝트 WaferSense AI는 보관 브랜치로 분리했습니다. 이전 코드의 테스트 결과도 FieldMemory의 검증 결과에 포함하지 않았습니다. 프로젝트의 목적이 바뀌었으니 테스트와 평가의 기준도 새로 세웠습니다.

## 문서를 등록하고 승인하는 흐름

자료를 모으는 기능부터 만들었습니다. Markdown, TXT, 텍스트 PDF와 DOCX를 가져오고, 업로드한 원본 바이트와 추출한 본문을 구분해 보관했습니다. 같은 파일명이어도 내용이 다를 수 있고, 추출 결과만 남기면 원본을 다시 확인하기 어렵기 때문입니다.

등록한 문서는 곧바로 승인된 근거가 되지 않습니다. 검토자가 본문, 자료 종류, 적용 대상과 효력 기간을 확인해야 합니다. 승인된 본문을 수정할 때에는 기존 승인본을 덮어쓰지 않고 새 버전의 초안을 만듭니다. 문서가 개정돼도 과거 기준일의 질문에 당시 자료를 찾을 수 있게 했습니다.

자료 종류도 구분했습니다. 공식 지침과 사건 기록, 경험 메모는 서로 다른 근거입니다. 경험 메모를 검토하고 승인했다는 이유로 그 내용이 공식 정책을 대신하지 않도록, 답변에서도 자료의 권위를 구분합니다.

여러 파일을 한 번에 올릴 때의 실패도 다뤘습니다. 일부 파일이 실패했는데 나머지만 등록되면 사용자가 예상한 자료실 상태와 달라집니다. 업로드 묶음을 모두 저장하거나 취소하도록 보완했습니다. PDF의 일부 페이지에 읽지 못한 이미지가 있다면 페이지 번호를 안내하고 등록을 중단합니다. 텍스트를 읽지 못한 페이지를 빈 내용으로 성공 처리하지 않았습니다.

이 과정에서 저장 기능은 파일을 넣는 것뿐 아니라, 실패했을 때 어떤 상태를 남길지까지 정해야 한다는 점을 확인했습니다.

## 의미 검색과 원문 연결

문서 제목과 사용자의 질문은 표현이 다릅니다. “다음 담당자에게 뭘 남겨야 하지?”라는 질문이 “교대 인수인계 기록 기준”의 필요한 문단으로 이어져야 합니다. 기본 검색에는 질문과 문단을 벡터로 표현하는 임베딩을 사용했습니다.

문단을 나눌 때에는 원문의 위치도 함께 남겼습니다. 최대 20개의 검색 후보 중 최대 5개 문단을 답변 문맥으로 사용하고, 인용에 문서 ID, 버전, 본문 해시와 줄 범위를 연결했습니다. 사용자가 답변 옆에서 실제 문장을 확인할 수 있어야 했기 때문입니다.

검색에는 질문 기준일과 적용 대상을 반영했습니다. 과거 승인본, 현재 승인본과 미래 초안이 같은 단어를 포함해도 사용할 자격은 다릅니다. 당시 승인되고 효력 기간에 들어오는 자료를 찾으며, 선택한 설비와 무관한 자료는 제외합니다. 같은 문서 묶음의 유효한 승인본이 겹치면 충돌을 표시합니다.

모델이나 색인이 준비되지 않았을 때의 동작도 명시했습니다. 화면은 필요한 준비를 안내합니다. 사용자가 키워드 검색을 선택할 수는 있지만, 임베딩 준비 실패를 숨기고 검색 방식을 자동으로 바꾸지는 않습니다.

문서가 수정되거나 철회되면 자료 개정 번호를 바꿉니다. 색인과 이미 표시한 답변은 이 번호로 현재 자료와 맞는지 확인합니다. 문서를 잘 찾았어도 그 뒤에 자료가 바뀌었다면, 같은 답변을 계속 현재 결과로 보여 줄 수 없기 때문입니다.

## 화면 시안을 실제 앱에 적용하기

초기에 남아 있던 UI 작업은 정적 시안이었습니다. 화면에 문서 목록이나 검색 결과가 보이는 것과, 실제 저장소에서 값을 읽어 동작하는 것은 구현 단계가 달랐습니다. MVP를 만든 뒤에는 제공된 Executive Slate 디자인을 Streamlit 화면에 적용했습니다.

검색 홈에 질문 입력, 설비와 기준일, 문서 현황을 배치하고 검색·문서·평가 화면을 연결했습니다. 승인 문서 수에는 철회하거나 재검토가 필요한 문서를 포함하지 않도록 집계도 고쳤습니다. 부서 관리, 외부 서비스 연동과 관리자 화면의 디자인 예시는 구현된 운영 기능으로 표시하지 않았습니다.

![합성 자료를 불러온 FieldMemory AI 검색 홈](/images/fieldmemory-ai/workspace-home-desktop.png)

*2026년 9월 28일 Windows 로컬 앱에서 확인한 검색 홈입니다. 화면의 문서는 가상 자료입니다.*

이후에는 검색창과 날짜 입력의 정렬, 좁은 화면에서의 잘림, 검색 후 읽는 순서를 다듬었습니다. 검색 결과가 나오면 질문과 조건을 작은 요약으로 표시하고, 입력 영역은 펼쳐서 수정할 수 있게 했습니다. 인용을 선택하면 정확한 원문 카드로 이동하고 선택한 카드만 강조합니다. 같은 인용을 다시 선택하거나 키보드로 열 때에도 동작을 유지했습니다.

![검색 결과와 선택한 원문을 함께 읽는 화면](/images/fieldmemory-ai/search-reading-desktop.png)

*2026년 10월 5일에 기록한 실제 로컬 화면입니다. 로컬 임베딩 검색의 원문 발췌를 보여 주며, 생성 LLM의 답변 화면은 아닙니다.*

원문을 펼치는 동작은 이미 찾은 근거를 읽는 일입니다. 여기서 검색이나 AI 생성을 다시 실행하지 않도록 했습니다. 질문이나 설정을 고치러 다른 화면에 갔다가 돌아와도 입력한 질문을 유지하는 흐름도 함께 확인했습니다.

## OpenRouter 연결과 실제 호출 기록

초기 연결은 Gemini와 기관 내부의 호환 API를 대상으로 구현했습니다. 이후 OpenRouter 지원을 추가했고, 사용할 모델이 정해지지 않은 경우에는 `openrouter/free`를 선택하는 버튼을 넣었습니다. 이 라우터는 요청 기능을 지원하는 무료 모델 중 하나를 선택합니다. [OpenRouter 공식 안내](https://openrouter.ai/docs/guides/routing/routers/free-router)에 선택 방식이 설명돼 있습니다.

연결은 합성 테스트와 설정 저장을 거쳐야 사용하도록 했습니다. 테스트에는 업무 문서 대신 작은 가상 문장을 사용하고, 응답의 JSON 구조와 인용 값을 확인합니다. 키나 모델을 바꾸면 이전 테스트 결과를 폐기합니다. 모델 선택 버튼을 눌렀다는 이유만으로 업무 질문을 전송하지 않습니다.

무료 라우터에서는 요청한 모델 이름과 실제 응답 모델이 다를 수 있습니다. 그래서 두 값을 나눠 기록하고, 제공자가 반환한 토큰 사용량과 앱이 측정한 호출 시간도 남기도록 개선했습니다. 응답에 없는 사용량은 0으로 채우지 않고 미제공으로 표시했습니다. 모델이 달라진 실행을 같은 조건의 성능 비교로 묶지 않도록 평가에도 이 정보를 연결했습니다.

연결 실패 시에는 원문 근거를 유지하고 원인별 안내를 표시합니다. 설정을 확인하러 이동해도 질문은 남기고, 다시 검색하기 전에는 호출하지 않습니다. 내부 LLM 연결이 실패했다고 외부 API로 자동 전환하는 경로도 만들지 않았습니다.

여기서 확인한 것은 연결 관리와 오류 처리의 구현입니다. 실제 계정으로 얻은 LLM 답변 정확도와 공급자 호환성 검증은 아직 남아 있습니다.

## 검색 평가에서 드러난 한계

검색을 구현한 뒤에는 합성 자료로 기준 평가를 만들었습니다. 공개 시연 자료와 개발·최종 평가 자료를 나눠, 시연에 사용한 질문이 그대로 성능 수치가 되지 않도록 했습니다. 평가 정답은 검색 색인이나 모델 입력에 넣지 않았습니다.

9월 28일의 최종 40문항 검색 평가에서는 답할 수 있는 24문항의 필수 문서를 상위 5개 안에서 모두 찾았습니다. 키워드 검색도 같은 결과였습니다. 자료가 짧고 중복 어휘가 많아 이 결과로 의미 검색이 더 낫다고 말하기는 어려웠습니다.

10월에는 여러 조건과 근거 누락을 다루는 evidence-v2 자료를 추가했습니다. 10월 7일 수정된 코드에서 개발 세트 30문항을 로컬 E5 모델로 다시 실행한 결과는 다음과 같습니다.

| 확인한 지표 | 결과 |
| --- | --- |
| 정답 원문 구간의 문단 회수 | 후보 20개와 선택 문맥 5개에서 각각 27/27 |
| 답 가능한 질문의 전체 근거 확보 | 후보·문맥에서 각각 18/18 |
| 보류가 필요한 질문의 상태 재현 | 6/12 |
| 실행 실패 | 0/30 |
| 실제 LLM·Jev 호출 | 0회 |
| 생성 답변 정확도 | 미측정 |

근거를 잘 찾은 수치와 함께 보류가 필요한 질문의 절반만 해당 상태로 처리했다는 결과도 남겼습니다. 검색 전용 경로는 자료에 없는 수치나 사실을 일반적인 의미 수준에서 판단하지 못합니다. 관련 문서를 찾았다고 그 문서가 질문의 모든 조건을 충족하는 것은 아니었습니다.

이 문제를 다루기 위해 질문에 필요한 정보를 추출하고, 선택한 근거가 그 정보를 충족하는지 확인한 다음, 충분할 때 답변을 생성하는 선택형 경로를 구현했습니다. 기본값은 꺼짐입니다. 자료 부족과 판단 실패를 구분하고, 단계별 호출과 사용량을 남깁니다. 이 경로의 실제 판단 품질은 별도로 검증해야 합니다.

Jev도 검색 후보 재정렬과 주장·근거 검증을 각각 선택할 수 있도록 구현했습니다. 비교할 때에는 같은 후보나 저장된 답변을 재사용합니다. 실패하거나 보류한 문항도 평가의 분모에 남깁니다. 현재 기록한 것은 비교 실행 구조와 오류 처리이며, 실제 Jev 적용 후의 정확도 개선률은 아직 측정하지 않았습니다.

## 반복 검토에서 고친 문제

기본 흐름이 동작한 뒤에도 검토와 사용 과정에서 문제가 이어졌습니다. 참조 원문을 다시 확인한 초안을 승인하는 흐름, 철회된 최신 버전 이후 새 초안을 만드는 흐름, 오래된 연결 설정의 주소를 키 손실 없이 고치는 흐름을 보완했습니다. 평가에서는 문서 ID뿐 아니라 정답 원문의 줄 구간이 실제 문맥에 들어왔는지 확인하도록 고쳤습니다.

마지막으로는 네 문제를 순서대로 수정했습니다.

1. **종료일 지정과 빈 날짜를 구분했습니다.** 종료일을 지정한 채 날짜를 비우면 저장·승인을 막고 입력을 유지합니다. 사용자가 종료일 지정을 해제한 경우에만 종료일 없는 상태를 허용합니다.
2. **단위 지수의 잘림을 막았습니다.** 처음에는 괄호나 위첨자처럼 지원하지 않는 지수 표기가 문제였습니다. 마지막 독립 검토에서는 `s^2x`처럼 정수 지수 뒤의 문자를 놓치는 경우도 찾았습니다. 완전히 해석하지 못한 표기는 생성 답변을 통과시키지 않고 원문으로 돌아가도록 보완했습니다. 정상적인 정수 지수와 한국어 어미는 유지했습니다.
3. **답변 검증 뒤의 자료 변경도 처리했습니다.** 검증 직후나 화면에서 출처를 읽는 동안 문서가 삭제·변경되면 결과를 지우고 다시 검색하도록 안내합니다. 질문은 유지하며 자동으로 모델을 다시 호출하지 않습니다.
4. **승인본 기간 종료의 빈 날짜 오류를 처리했습니다.** 화면에 입력 안내를 표시하고, 저장소에서도 잘못된 날짜를 거절합니다. 실패한 입력은 원문과 승인·기간 이력을 바꾸지 않으며, 날짜를 보완하면 다시 저장할 수 있습니다.

특히 지수 문제는 첫 수정이 끝난 뒤의 독립 검토에서 다시 발견됐습니다. 추가 사례를 테스트로 만들자 수정 전에는 15개가 실패했습니다. 이후 파싱 경계를 보완하고 관련 검사를 다시 통과시켰습니다. 처음 발견한 예시를 막았다고 같은 종류의 오류가 모두 해결된 것은 아니었습니다.

네 수정과 마지막 경계 보완에서 사용자 행동 사례 50개를 추가했습니다. 10월 7일 macOS·Python 3.11.16의 최종 제품 테스트는 **729개 통과, Windows 전용 4개 제외**였습니다. 제외한 검사는 이 Mac에 PowerShell이 없어 실행하지 못한 항목입니다. 이를 최신 수정의 Windows 통과 결과로 세지 않았습니다. 자료 해시·정답 구간·문서 링크 검사와 Ruff 검사도 통과했습니다.

## AI와 함께 개발한 방식

설계와 코드 초안, 테스트 작성, 문제 재현과 검토에는 Codex를 활용했고 Superpowers 지침을 적용했습니다. 구현과 검토를 분리해 같은 변경을 다시 읽게 했으며, 지적된 문제는 실제 동작에서 재현되는지 확인한 뒤 수정했습니다.

오류를 고칠 때에는 문제가 생기는 사용자 행동을 먼저 테스트로 만들었습니다. 빈 날짜로 저장하기, 답변 검증 중 문서 삭제하기, 인용을 다시 선택하기처럼 상황을 좁혀 실패를 확인하고, 수정 뒤에는 해당 테스트와 기존 흐름을 함께 검사했습니다. AI가 작성한 테스트와 코드도 이 과정을 거쳐 확인했습니다.

검증의 종류를 분리해 기록한 것도 이 작업 방식의 일부입니다. 자료 검사는 파일 해시와 참조의 일치 여부를 확인합니다. 제품 테스트는 임시 저장소와 생성기 대역으로 동작을 확인합니다. 실제 로컬 임베딩 검색은 모델을 실행한 검색 결과입니다. 어느 것도 실제 LLM 답변의 정답률을 대신하지 않습니다.

## 현재 상태와 다음 검증

현재는 한 사용자가 한 팀의 자료를 관리하는 로컬 MVP입니다. 문서 등록·검토·버전 관리, 임베딩 검색, 원문 확인과 외부·내부 LLM 연결 경로를 구현했습니다. 경험 인터뷰, 외부 서비스의 자동 수집, 조직 권한과 다중 사용자 운영은 후속 범위입니다.

10월 8일 기준 GitHub 기본 브랜치에는 기존 MVP와 OpenRouter 연결, 화면 캡처까지 반영돼 있습니다. 근거 충분성·최근 검색 UI 작업은 초안 PR에 있고, 10월 7일의 통합·추가 오류 수정은 로컬 작업 브랜치에 커밋한 상태입니다. 이 글의 최신 구현 내용이 모두 기본 브랜치에 합쳐진 상태는 아닙니다.

다음 검증은 모델을 고정한 실제 LLM 실행과 답변의 독립 판정입니다. 근거 충분성 확인을 켰을 때 불필요한 보류와 근거 없는 답변이 어떻게 달라지는지, Jev를 적용했을 때 같은 조건에서 변화가 있는지 확인해야 합니다. 실제 팀 문서로 평가하려면 자료와 사용 권한도 별도로 준비해야 합니다.

FieldMemory AI를 만들며 문서의 상태, 입력값, 원문 위치와 평가 조건을 하나씩 구체화했습니다. 문서를 찾은 결과가 화면에 나오기까지 여러 단계가 있고, 각 단계가 바뀌거나 실패했을 때의 동작도 필요했습니다. 앞으로의 모델 실험에서도 어떤 근거로 무엇을 확인했는지 남기는 방식을 이어 가려 합니다.
