기존에 개발하던 Python 기반 업비트 자동매매 프로젝트를 다시 점검했다. 매수·매도 조건을 살펴보고, 거래 기록과 성과 계산을 보완하고, 웹 대시보드도 개편했다. 마지막으로 Ubuntu 개발 서버에서 실행할 수 있도록 배포 구성을 준비했다.

코드 검토에서 발견한 문제를 테스트로 재현하고, 수정 후에는 별도 리뷰로 놓친 경로를 확인하는 방식으로 진행했다. 봇의 매매 판단은 코드에 정의한 볼린저 밴드 규칙을 따른다.

이번 글은 그 과정에서 발견한 문제와 수정한 내용을 정리한 개발 기록이다.

> 이 글은 자동매매 시스템의 설계와 검증을 정리한 개발 기록이며 투자 권유가 아니다. 아래 검증은 외부 API 호출과 실제 자금 주문을 차단한 환경에서 진행했으며, 전략의 실전 수익성을 입증하지 않는다.

## 1. 프로젝트는 어떻게 구성되어 있나

프로젝트의 주요 구성은 다음과 같다.

| 영역 | 사용 기술과 역할 |
| --- | --- |
| 시세·거래소 연동 | Python, pyupbit |
| 지표 계산 | pandas, NumPy, 볼린저 밴드 |
| 웹 서버 | FastAPI, Uvicorn |
| 대시보드 | Jinja2, HTML, CSS, JavaScript |
| 서버 실행 구성 | Ubuntu, Python 가상환경, systemd |

실행 모드는 세 가지로 나누었다.

- **dry**: 매수·매도 신호를 감지하고 기록한다.
- **paper**: 시세를 바탕으로 가상 잔고와 모의 체결을 관리한다.
- **real**: API 키와 실전 설정을 사용해 실제 주문을 전송한다.

기본 전략은 볼린저 밴드 경계의 교차를 이용한다. 마감된 봉을 기준으로 가격이 하단선 아래로 내려가는 교차가 발생하면 매수하고, 보유 중 상단선 위로 올라가는 교차가 발생하면 매도한다. 보유 중 추가 매수는 하지 않는다.

여기서 매수 조건에 반등 확인은 포함되어 있지 않다. 이 점을 정확히 설명하도록 코드 주석도 정리했다. 전략 조건을 읽는 사람이 실제 구현보다 강한 의미로 해석하지 않게 하기 위해서다.

## 2. 매매 로직을 검토하며 발견한 다섯 가지 문제

### 봇이 매수한 수량과 계좌 전체 잔고가 섞여 있었다

가장 먼저 수정한 부분은 매도 수량이었다.

기존 코드에는 해당 코인의 사용 가능 잔고 전체를 매도 주문에 사용하는 경로가 있었다. 봇이 매수한 수량이 2개이고 계좌에 5개가 있다면, 수동으로 보유하던 3개까지 주문 대상이 될 수 있었다.

수정 후에는 봇의 확정된 매수 기록에 남은 수량만 매도하도록 제한했다. 저장된 수량이 없거나 실제 가용 수량이 부족하면 자동 거래를 보류한다. 나중에 입금되어 잔고가 늘더라도 이를 봇의 보유 수량으로 추정하지 않는다.

리뷰 과정에서는 과거 미확인 주문을 복구할 때도 같은 문제가 발생할 수 있다는 점을 발견했다. 오래된 주문의 요청 수량을 그대로 봇의 잔량으로 가져오지 않도록 복구 경로까지 보완했다.

### 웹에서 시작한 실전 봇이 터미널 입력을 기다렸다

CLI에서는 실전 모드 실행 전에 확인 입력을 받도록 되어 있었다. 그런데 웹 서버가 봇을 자식 프로세스로 실행할 때도 이 확인 과정에 들어가고 있었다.

사용자가 입력할 터미널이 없는 환경에서는 봇이 종료되거나 입력을 기다릴 수 있다. 웹 화면에서 시작 버튼을 눌렀다고 해서 매매 루프에 도달한 것은 아니었다.

웹의 실전 실행 경로에는 비대화형 확인 옵션을 전달하고 표준입력을 분리했다. 일반 CLI에서 직접 실행할 때의 확인 절차는 유지했다. 테스트에서는 웹이 만든 명령을 실제 CLI 파서에 넣어 봇 실행 함수까지 도달하는지 확인했다.

### 손절 직후 같은 봉으로 다시 매수할 수 있었다

손절과 매수 신호가 같은 시점에 겹치는 경우도 살펴봤다.

기존 로직은 손절을 처리한 뒤 해당 봉을 이미 처리했다는 기록을 남기기 전에 반환했다. 다음 가격 확인 주기에서 같은 봉의 매수 신호를 다시 평가할 수 있었다.

재현 데이터에서는 다음과 같은 흐름이 나타났다.

```text
손절 매도 → 같은 봉으로 재매수 → 다시 손절
```

수정 후에는 손절에 사용한 마감 봉의 시각을 저장한다. 같은 봉의 신호는 다시 매수에 사용하지 않으며, 재시작 후에도 이 기록을 복원한다.

손절 자체는 매 가격 확인 주기마다 계속 점검한다. 시장가 주문으로 실행하므로 설정한 손절률과 실제 확정 손실률은 달라질 수 있다.

### 매수 금액 계산에서 수수료를 위한 여유가 없었다

잔고와 주문 한도가 각각 100,000원이고 매수 비중이 100%라고 가정해 보자. 주문가액을 그대로 100,000원으로 잡으면 별도로 필요한 매수 수수료 때문에 잔고 부족이 발생할 수 있다.

수정한 계산 기준은 다음과 같다.

```text
총지출 한도 = min(가용 현금 × 매수 비중, 설정 한도, 가용 현금)
주문가액 = 총지출 한도 ÷ (1 + 적용 매수 수수료율)
```

적용 수수료율이 0.05%인 예시에서는 주문가액을 0.01원 단위로 내려 **99,950.02원**으로 계산한다. 수수료를 포함한 지출이 한도 안에 들어오도록 한 것이다.

실전 계산에는 거래소 API에서 조회한 적용 매수 수수료율을 사용한다. 수수료를 조회하지 못하면 매수를 보류한다. 예시의 0.05%를 모든 거래에 고정해서 사용하는 방식은 아니다.

### 모의 거래가 이미 지나간 종가로 체결되고 있었다

신호를 판단하는 가격과 주문을 실행하는 시점의 가격도 구분해야 했다.

예를 들어 마감 봉 종가가 80이고 현재 관측 가격이 75라면, 신호는 마감 봉으로 판단하되 모의 체결에는 75를 사용해야 한다. 기존 코드는 전달받은 과거 종가 80을 모의 체결가로 기록하고 있었다.

수정 후에는 최신 봉에서 관측한 가격으로 모의 거래를 체결한다. 유효한 현재 가격이 없으면 해당 판단을 건너뛴다.

다만 이 모의 체결 모델은 수수료를 반영하면서 슬리피지는 0으로 가정한다. 호가와 유동성까지 재현하는 모델은 아니므로 실제 체결과 차이가 생길 수 있다.

## 3. 체결 확인과 수수료 후 손익을 기준으로 기록하기

주문 요청을 보낸 뒤 응답이 오지 않는 상황도 고려했다. 이때 요청을 바로 다시 보내면 이미 접수된 주문과 중복될 수 있다.

현재 실전 주문 처리는 다음 순서를 따른다.

```text
주문 식별자와 의도 저장
→ 주문 전송
→ 같은 식별자로 체결 결과 조회
→ 확정된 거래 기록 저장
→ 미확인 주문 상태 해제
```

조회가 실패하거나 아직 체결이 확인되지 않으면 미확인 상태를 유지한다. 재시작 후에도 저장한 식별자로 확인을 이어간다. 부분 체결 후 취소된 경우에는 실제 체결량만 기록하고 남은 봇 수량을 관리한다.

성과 계산도 실제 현금 흐름을 기준으로 정리했다.

- 매수 총지출: 체결대금 + 매수 수수료
- 매도 순수령액: 체결대금 − 매도 수수료
- 순손익: 매도 순수령액 − 매도 수량에 해당하는 매수 총원가

가격이 조금 올랐더라도 수수료를 뺀 결과는 손실일 수 있다. 승률 역시 순손익이 확인된 매도 거래를 기준으로 계산하도록 했다.

원가나 초기자금이 없는 기록은 임의의 숫자로 채우지 않는다. 확인할 수 없는 성과는 화면에서도 미확인으로 표시한다.

## 4. 대시보드에서 확인해야 할 정보를 먼저 배치하기

웹 화면도 색상과 레이아웃을 전면적으로 정리했다. 밝은 본문, 네이비 메뉴, 파란색 주요 버튼을 사용하고 대시보드·설정·로그인의 스타일을 맞췄다.

배치 기준은 봇을 운영할 때 자주 확인하는 정보였다.

- 현재 실행 모드와 봇 상태
- 시작·중지 버튼
- 보유 상태와 포트폴리오 요약
- 거래 내역과 성과
- 실행 로그

모드와 실행 상태는 탭을 바꾸어도 볼 수 있도록 두었다. 거래 현황·성과 분석·로그는 탭으로 나누고, 모바일에서는 카드 형태로 읽을 수 있게 조정했다.

설정 화면의 비중과 손절률은 `30%`, `5%`처럼 입력하도록 바꿨다. 저장할 때는 내부에서 사용하는 비율로 변환한다. 요청 처리 중 중복 클릭을 막고, 저장에 실패하면 입력값과 오류 안내를 유지하도록 했다.

화면 검증에는 예시 데이터를 사용했고, 매매 로직은 거래소 API를 대신하는 테스트 객체로 검증했다. 화면에 보이는 숫자와 실제 계좌 성과를 혼동하지 않도록 검증 환경도 구분했다.

## 5. Ubuntu 서버에서 실행할 준비

배포 대상은 Ubuntu로 정했다. SSH 주소와 인증 정보는 직접 적용하고, 프로젝트에는 서버 설치와 실행에 필요한 구성을 추가했다.

설치 스크립트는 Python 가상환경을 만들고 의존성을 설치한 뒤 systemd 서비스 파일을 생성한다. 새 설치의 기본값은 다음과 같다.

- `paper` 모드
- 봇 자동 시작 끄기
- 서버 내부 주소 `127.0.0.1`에 바인딩
- Uvicorn 워커 1개
- 로그인 키를 서버에서 생성해 권한 `0600`으로 저장

따라서 처음 서비스를 시작하면 웹 대시보드가 뜨고, 모의 봇 실행은 대시보드에서 시작할 수 있다. 브라우저 접속은 SSH 터널을 사용하는 구성으로 준비했다.

웹 프로세스의 복구와 봇의 자동 재시작은 별도 설정이다. systemd는 웹 프로세스가 비정상 종료됐을 때 복구를 담당하고, 봇 자동 재시작은 대시보드 설정이 결정한다.

배포 압축 파일에는 현재 수정한 소스를 담되 실제 `.env`, 거래 기록, 포지션 파일, 로그, 가상환경은 제외했다. 재설치할 때도 서버에 이미 있는 키와 거래 상태는 보존하도록 했다.

## 6. 어디까지 검증했나

Ubuntu 배포 준비까지 포함한 마지막 격리 테스트 결과는 다음과 같다.

```text
510 passed, 5 warnings
```

기존 LibreSSL/urllib3 및 FastAPI 관련 경고는 남아 있다. 새로 추가한 배포 테스트에서는 초기 설정 생성, 재설치 시 기존 파일 보존, 잘못된 설정 차단, 압축 파일의 런타임 데이터 제외 등을 확인했다.

임시 프로젝트에서 실제 로컬 HTTP 서버를 실행한 결과도 확인했다.

| 확인 항목 | 결과 |
| --- | --- |
| 로그인 페이지 | HTTP 200 |
| 인증 없이 API 접근 | HTTP 401 |
| 인증 후 설정 페이지 | HTTP 200 |
| 최초 매매 모드 | paper |
| 최초 봇 상태 | 정지 |
| 웹 서버 종료 | 정상 종료 절차 확인 |

이 검증은 macOS의 격리 환경에서 진행했다. 외부 API 호출을 차단했고 실제 자금으로 주문하지 않았다. Ubuntu 서버의 패키지 설치와 systemd 구동은 서버에서 확인할 단계로 남아 있다.

또한 테스트 통과는 재현한 상황에서 코드가 기대한 대로 동작한다는 의미다. 전략의 실전 수익성이 검증되었다는 뜻은 아니다.

## 마무리

이번 작업을 통해 매매 신호 이후에 확인해야 할 항목이 구체적으로 드러났다. 봇이 관리하는 수량, 실제 체결 결과, 수수료를 포함한 지출, 재시작 후 복원할 상태가 서로 일관되어야 했다.

코드 리뷰와 회귀 테스트는 그 연결을 확인하는 데 도움이 됐다. 특히 정상적인 신규 주문뿐 아니라 과거 미확인 주문을 복구하는 경로까지 검토하면서 추가 문제를 발견할 수 있었다.

다음 단계는 Ubuntu 서버에서 모의 운영을 진행하며 로그와 상태 복구를 확인하는 것이다. 그 이후에는 거래 비용과 체결 차이를 반영해 여러 시장 구간에서 전략을 비교해 볼 계획이다.
