배드민턴 경기 영상 위에 선수 네 명의 박스가 나타났습니다. 번호도 1번부터 4번까지 붙었습니다. 새로 학습한 선수 검출 모델이 잘 동작하는 것처럼 보였습니다.

그런데 로그를 확인하니 다른 이야기가 나왔습니다. 새 모델이 놓친 선수를 기존 범용 모델이 대신 찾고 있었습니다. 화면에 네 명이 보인다는 사실만으로는, 제가 개선하려던 부분이 실제로 좋아졌는지 알 수 없었습니다.

BadmintonAI를 만들면서 이런 순간을 여러 번 겪었습니다. 느린 원인을 잘못 짚었고, 정상적으로 만들어진 결과 영상 뒤에서 모델이 바뀌는 것도 놓쳤습니다. 테스트가 통과했는데 정작 아무것도 검증하지 않는 경우도 있었습니다.

이 글은 배드민턴 복식 경기 영상을 아이폰 안에서 분석하는 앱을 만들며, 그런 착각을 하나씩 확인하고 고친 기록입니다.

> BadmintonAI는 사업화를 고려하며 개발 중인 프로젝트입니다. 이 글에서는 문제 정의와 기술적 의사결정, 검증 결과를 공유합니다. [GitHub 포트폴리오](https://github.com/beckspeca/BadmintonAI)에는 프로젝트 소개와 검증 결과·기술적 판단 요약만 공개합니다. 앱 소스코드, 핵심 분석 로직, 상세 설계, 학습·변환 도구, 모델 가중치와 경기 영상·학습 데이터는 공개본에 포함하지 않습니다. 아래 수치는 개발 기록의 특정 기기·데이터·실험 조건에서 얻은 결과이며, 제품 전체의 정확도나 모든 환경에서의 성능을 보장하지 않습니다.

## 경기 영상 하나를 분석하기까지

BadmintonAI는 코트를 찾고, 선수 네 명을 추적하고, 셔틀콕의 궤적과 타격 시점을 추정하는 앱입니다. 분석은 영상을 서버로 전송하지 않고 아이폰에서 수행합니다.

배드민턴 복식에는 까다로운 조건이 겹쳐 있습니다. 좁은 코트에서 선수들이 자주 겹치고, 반대편 코트의 선수는 작게 보입니다. 셔틀콕은 화면에서 몇 픽셀에 불과한데 빠르게 움직입니다. 체육관마다 조명과 촬영 각도도 다릅니다.

영상이 들어오면 다음 과정을 거칩니다.

| 단계 | 처리하는 내용 |
| --- | --- |
| 코트 검출 | 코트 영역을 찾고 영상 좌표를 실제 코트 좌표에 대응시킵니다. |
| 셔틀 추적 | 연속 프레임과 배경 이미지를 이용해 셔틀콕 위치를 추정합니다. |
| 선수 검출·추적 | 선수 네 명을 찾고 프레임 사이의 움직임을 연결합니다. |
| 타격·통계 | 셔틀 궤적의 방향 변화와 손목 움직임을 바탕으로 타격을 추정하고 이동 정보를 누적합니다. |
| 결과 생성 | 선수 박스와 번호, 궤적을 그린 영상과 JSON·CSV를 내보냅니다. |

셔틀 추적에는 TrackNetV3의 공개 체크포인트를 Core ML로 변환해 사용했습니다. 연속 프레임과 배경 이미지를 입력하면 셔틀콕이 있을 가능성을 나타내는 히트맵이 나옵니다. 여기서 좌표를 추출해 궤적으로 연결합니다.

현재 주 선수 검출기는 RF-DETR Nano입니다. 처음부터 이 모델을 사용한 것은 아닙니다.

이 프로젝트에서 다룬 개발 범위는 공개 모델을 바탕으로 한 배드민턴 데이터 추가 학습, Core ML 변환과 앱 통합, 영상 분석 파이프라인 구성, 실기기 성능 측정과 리팩터링입니다. 기반 모델을 처음부터 설계한 작업과는 구분합니다.

## 1. 전용으로 학습하면 더 잘 찾을 줄 알았다

처음에는 COCO 데이터로 학습된 `yolo11n`을 사용했습니다. 사람은 잘 찾았지만, 경기 중인 선수만 구분해 주지는 않았습니다. 심판과 코치, 관중까지 검출했습니다. 코트 영역으로 거르고 복식 선수 수를 제한하는 후처리만으로는 충분하지 않았습니다.

그래서 배드민턴 전용 YOLO11 모델을 학습했습니다.

학습에 앞서 규칙도 정했습니다. YOLO11s부터 시작하고, 데이터에 문제가 없다는 것을 확인한 뒤에만 더 큰 모델을 비교하기로 했습니다. 원거리의 작은 선수를 놓치는 문제를 모델 크기로 덮고 싶지는 않았습니다.

데이터를 나누는 기준도 경기 원본으로 잡았습니다. 같은 영상의 인접 프레임이 학습과 검증에 들어가면 거의 같은 장면으로 시험을 보는 셈이기 때문입니다.

그런데 앱에 넣은 전용 모델은 기대보다 못했습니다.

결과 화면에는 선수 네 명이 나타났지만, 실제 검출의 상당 부분은 보완용으로 남겨 둔 범용 모델이 담당하고 있었습니다. 학습 데이터에 실전 경기 장면과 원거리의 작은 선수 라벨이 부족했습니다.

이때 바로 다음 모델을 학습하는 대신, 실패 장면을 수집하는 도구부터 만들었습니다.

검출된 선수가 네 명보다 적거나, 예측 좌표로 선수를 보완했거나, 신뢰도가 낮은 구간을 분석 결과에서 찾아 원본 프레임을 추출했습니다. 작은 선수와 겹친 선수, 코트 밖으로 이동한 장면도 수집 대상에 넣었습니다.

같은 실패가 오래 이어진다고 모든 프레임을 저장하지는 않았습니다. 비슷한 장면이 데이터셋을 채우지 않도록 대표 구간을 남겼습니다.

**다음 학습에서 무엇을 바꿔야 할지 알려면, 지금 모델이 어디서 실패하는지부터 모아야 했습니다.**

이후 YOLO11 v2 대신 RF-DETR Nano로 전환했고, 배드민턴 라벨 이미지 542장으로 추가 학습했습니다.

| 지표 | 기존 검출기 | RF-DETR |
| --- | ---: | ---: |
| 재현율 | 75.9% | 94.0% |
| 정밀도 | 43.0% | 96.5% |
| 오검출 | 233개 | 8개 |
| 작은 선수 재현율 | 69.0% | 92.0% |
| 네 명을 모두 찾고 오검출이 없는 프레임 | 20.7% | 74.1% |

정밀도는 검출한 결과 중 실제 선수가 얼마나 되는지를, 재현율은 실제 선수 중 얼마나 찾아냈는지를 나타냅니다. 특히 네 명을 모두 찾으면서 엉뚱한 검출도 없는 프레임의 비율이 오른 것이 앱의 목적에 잘 맞는 변화였습니다.

다만 이 수치를 앱 전체의 정확도로 볼 수는 없습니다. 평가는 원본 영상 11개에서 얻은 이미지 58장, 선수 정답 박스 232개를 대상으로 했습니다. 코트 필터 적용 전 검출 결과를 정답 박스와 IoU 0.5 이상으로 일대일 대응시킨 결과입니다. 선수 번호가 경기 내내 유지되는지, 타격 시점이 맞는지는 별도로 검증해야 합니다.

평가 자료의 이력에도 한계가 있습니다. RF-DETR 학습과 설정 선택에는 사용하지 않았지만, 과거 YOLO 검증 자료 140장을 이번 검증·테스트로 나누어 사용했습니다. 모든 모델에 완전히 새로운 시험이었다고 말할 수는 없습니다.

따라서 이 결과는 이번 데이터와 학습·평가 조건에서 얻은 개선입니다. 아키텍처만 바꾸면 같은 향상이 난다는 뜻은 아닙니다.

## 2. 느린 곳을 측정했더니 모델 밖이었다

분석 속도를 개선할 때는 단계별 시간을 먼저 기록했습니다. 그 과정에서 프레임 읽기, 영상 합성, 히트맵 후처리에 큰 비용이 숨어 있다는 것을 확인했습니다.

셔틀 분석 경로에서는 `AVAssetImageGenerator`로 필요한 시점의 이미지를 각각 요청하고 있었습니다. 이를 `AVAssetReader`로 순차적으로 읽도록 바꾸고, 크기 축소도 디코더에 맡겼습니다.

해당 실험에서 프레임 읽기와 크기 변환은 19.73초에서 0.72초로 줄었습니다. 선수 분석 경로에도 같은 원리를 적용하자 프레임 읽기가 18.11초에서 0.28초로 줄었습니다.

결과 영상 합성에도 불필요한 작업이 있었습니다. 코트를 그린 이미지와 선수 박스를 그린 이미지를 따로 만들고, 다시 저장용 프레임으로 복사하고 있었습니다. 화면 배율이 3배인 기기에서는 중간 이미지의 픽셀 수가 저장 해상도의 9배가 됐습니다.

저장할 프레임에 한 번에 그리도록 바꾸자 프레임당 합성 시간은 59.67ms에서 2.62ms로 줄었습니다.

| 개선 대상 | 변경 전 | 변경 후 |
| --- | ---: | ---: |
| 셔틀 프레임 읽기·크기 변환 | 19.73초 | 0.72초 |
| 선수 프레임 읽기 | 18.11초 | 0.28초 |
| 영상 합성 | 59.67ms/프레임 | 2.62ms/프레임 |

각 수치는 개별 최적화 실험의 해당 구간 측정값입니다. 합산해서 앱 전체의 단축 시간으로 계산할 수는 없습니다.

모델을 빠르게 실행하는 것만큼, 모델에 넣을 데이터를 어떻게 읽고 결과를 어떻게 저장하는지도 중요했습니다.

## 3. 측정값이 있어도 해석은 틀릴 수 있었다

셔틀 추적 모델의 출력은 좌표가 아닌 히트맵입니다. 좌표를 얻으려면 히트맵을 읽는 후처리가 필요합니다.

이 코드에서는 픽셀마다 `MLMultiArray`의 자료형을 확인하고 포인터를 다시 바인딩하고 있었습니다. 반복문 밖에서 한 번만 해도 되는 작업이었습니다.

문제는 최적화 이전에 제가 믿고 있던 측정값이었습니다. Debug 빌드에서는 히트맵 디코드가 셔틀 처리 시간의 92%를 차지했습니다. Release 빌드로 다시 측정하니 24%였습니다.

| 측정 항목 | Debug | Release |
| --- | ---: | ---: |
| 셔틀 처리 시간 중 디코드 비중 | 92% | 24% |
| 프레임당 디코드 시간 | 0.0998초 | 0.0028초 |

같은 코드와 기기, 영상이어도 빌드 최적화에 따라 병목의 모습이 크게 달라졌습니다. Debug 측정은 문제를 찾는 단서였지만, 사용자가 실행할 앱에서 그 문제가 얼마나 큰지는 다시 확인해야 했습니다.

반복 작업을 루프 밖으로 옮긴 뒤에는 iPhone 16·iOS 26.5의 Release 빌드에서 60초 영상 구간을 여덟 번 측정했습니다. 실행 순서는 변경 전을 A, 변경 후를 B로 두고 `A B B A A B B A`로 배치했습니다. 회차 사이에는 30초씩 쉬었습니다.

기기가 뜨거워지면서 뒤쪽 실행이 느려질 수 있으므로, 한 버전만 먼저 몰아서 실행하는 영향을 줄이려는 구성이었습니다.

| 측정 항목 | 변경 전 평균 | 변경 후 평균 |
| --- | ---: | ---: |
| 히트맵 디코드 | 12.06초 | 2.85초 |
| 셔틀 단계 전체 | 45.76초 | 37.10초 |
| 모델 추론 | 30.50초 | 31.44초 |

히트맵 디코드는 평균 76.4% 줄었습니다. 여덟 번 모두 셔틀 포인트 수는 1,381개였고 실패 배치는 없었습니다. 다만 이 두 지표가 같다는 사실만으로 모든 좌표가 완전히 동일하다고 단정할 수는 없습니다.

셔틀 단계 전체 시간도 평균 18.9% 줄었지만, 이 숫자는 더 조심해서 해석해야 합니다. 측정 전에 정했던 “같은 조건 안의 편차가 두 조건 사이의 차이보다 크면 결론을 내리지 않는다”는 기준에 걸렸기 때문입니다. 발열에 따른 시간 변화와 인접 실행 쌍의 비교를 근거로 개선을 해석했지만, 사전 기준을 그대로 적용한 결론은 아니었습니다.

37.10초는 60초 영상의 **셔틀 단계만** 측정한 값입니다. 선수 분석과 결과 영상 내보내기를 포함한 앱 전체 처리 시간은 아닙니다.

좋아진 숫자만 남기는 것도 경계해야 했습니다. 입력 복사 시간은 0.42초에서 0.66초로 늘었는데, 처음에는 큰 개선에 가려 보고에서 빠뜨렸습니다.

**측정값을 남기는 일과 그 측정값을 공정하게 설명하는 일은 별개의 작업이었습니다.**

## 4. 결과 영상이 나온다고 성공한 것은 아니었다

실제 아이폰에서는 백그라운드 실행 중 또 다른 문제가 드러났습니다.

분석 도중 앱을 백그라운드로 보내거나 화면을 잠그는 조건에서 GPU 작업이 거부됐습니다. 로그에는 다음 오류가 나타났습니다.

`kIOGPUCommandBufferCallbackErrorBackgroundExecutionNotPermitted`

이때 셔틀 추적이 실패했고, 선수 검출에서는 RF-DETR 대신 구형 검출기를 사용하는 폴백이 발생했습니다.

더 곤란한 점은 결과 영상이 계속 만들어졌다는 것입니다. 사용자에게는 정상적으로 분석이 끝난 것처럼 보이지만, 내부에서는 다른 검출기가 결과를 만들고 있었습니다.

앞선 평가에서 검출기 사이의 성능 차이를 이미 확인한 상태였습니다. 폴백은 단순히 앱이 멈추지 않게 하는 장치로만 볼 수 없었습니다. 결과 품질에도 영향을 주는 동작이었습니다.

컴퓨트 유닛 실패 시 Neural Engine을 사용하는 경로로 재시도하도록 수정했고, 해당 기기와 재검증 조건에서 다음 결과를 얻었습니다.

| 항목 | 수정 전 | 수정 후 |
| --- | ---: | ---: |
| GPU 작업 거부 | 832회 | 2회 |
| 선수 검출기 폴백 | 732회 | 0회 |

이 결과로 확인한 것은 해당 조건에서 실패와 검출기 전환이 크게 줄었다는 사실입니다. 모든 백그라운드 상황에서 분석이 끝까지 실행된다는 보장까지 얻은 것은 아닙니다.

이후에는 분석 완료 여부와 함께, 어떤 모델과 실행 경로가 결과를 만들었는지도 확인해야 한다는 기준이 생겼습니다.

## 5. 테스트도 실패하는지 확인해야 했다

기능을 붙이다 보니 `ContentView.swift`가 3,090줄까지 커졌습니다. 화면과 상태 관리, 분석 실행 흐름이 한 파일에 섞여 있었습니다.

네 차례에 걸쳐 결과 화면과 작은 뷰를 분리하고, 실행 흐름을 뷰 모델로 옮겼습니다. 최종적으로 `ContentView.swift`는 531줄이 됐습니다. 이 과정에서 단위 테스트는 25개에서 64개로 늘었습니다.

줄 수를 줄이는 것보다 중요했던 기준은 기존 동작을 유지했는지 확인하는 일이었습니다. 화면을 이동할 때는 본문이 그대로인지 비교했고, 실행 흐름을 옮길 때는 테스트를 추가했습니다.

테스트에는 일부러 잘못된 변경을 넣어 실제로 실패하는지도 확인했습니다. 이 과정에서 항상 통과하는 테스트 하나를 발견했습니다.

상태를 초기화한 뒤 값이 비어 있는지 확인하는 테스트였는데, 초기화하기 전에 값을 넣지 않았습니다. 초기화 코드가 아무 일도 하지 않아도 통과할 수 있었습니다.

테스트 개수가 늘었다는 사실만으로는 충분하지 않았습니다. 해당 동작이 깨졌을 때 테스트가 그 차이를 잡아내는지 확인해야 했습니다.

## 아직 확인하지 못한 것들

검출 정확도와 처리 시간을 개선했지만, 남은 검증도 분명합니다.

선수 검출은 정지 이미지로 평가했습니다. 연속 영상에서 선수 ID가 몇 번 바뀌는지는 아직 정답 라벨을 기준으로 측정하지 못했습니다. 네 명을 찾는 능력과 같은 선수를 끝까지 같은 번호로 추적하는 능력은 따로 확인해야 합니다.

포즈 분석에도 비용이 남아 있습니다. 기록된 측정에서 모델 추론은 4.8초였지만 전체 파이프라인은 36.6초였습니다. 전처리와 후처리를 더 살펴볼 필요가 있습니다.

메모리 접근 방식과 동시성 설정을 점검하고, 앱의 실제 기록 저장소를 사용하는 테스트도 분리해야 합니다.

이번 개발에서 남은 기준은 구체적입니다. 선수 네 명이 보이면 어떤 검출기가 찾았는지 확인하고, 속도가 빨라지면 배포 조건에서 다시 측정하고, 테스트가 통과하면 잘못된 동작도 잡아내는지 확인합니다.

다음 검증 과제는 연속 경기 영상에서 선수 ID의 일관성을 평가하는 것입니다. 이제는 네 명을 찾았는지에 더해, 경기 내내 같은 네 명을 따라갔는지 확인할 차례입니다.
