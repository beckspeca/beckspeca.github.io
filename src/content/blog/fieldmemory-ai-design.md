“이 업무를 넘겨받으면 무엇부터 확인해야 할까?”

인수인계를 받는 사람은 이전 담당자가 어디까지 처리했는지, 어떤 자료를 확인했는지, 아직 확인하지 못한 내용은 무엇인지 알아야 합니다. 그런데 업무 가이드, 교대 기록, 선임의 경험 메모에 필요한 정보가 나뉘어 있다면 문서를 찾아 읽고 서로 연결하는 일부터 시작해야 합니다.

관련 문서를 찾은 뒤에도 확인할 것이 있습니다. 인수인계 기준이 지금도 유효한지, 조치를 시도한 기록에 후속 결과까지 남아 있는지, 개인의 경험 메모를 공식 절차처럼 읽고 있지는 않은지 살펴봐야 합니다.

**FieldMemory AI는 팀의 업무 문서를 모아 질문에 맞는 근거를 찾고, 답변과 원문을 함께 확인할 수 있도록 설계 중인 프로젝트입니다.** 이 글에서는 인수인계 자료를 검색하는 상황을 중심으로 문서 조건 필터, 인용 구조, 재정렬·검증 실험과 평가 지표를 다룹니다.

> 2026년 9월 28일 기준 기획·설계와 정적 화면 시안, 합성 자료 15개, 개발·시연용 질문 예시 20개가 준비되어 있습니다. 검색·답변 생성·실제 LLM 연결은 아직 구현 전이며 성능은 미측정입니다. 이 글의 인수인계 사례는 모두 가상 자료를 바탕으로 구성했습니다.

## 인수인계 질문에서 어떤 근거를 찾아야 할까

교대나 담당자 변경 때 필요한 질문은 크게 두 가지입니다. 인수인계에 무엇을 남겨야 하는지 묻는 질문과, 특정 업무에서 실제로 어떤 일이 있었는지 묻는 질문입니다. 전자는 유효한 업무 지침에서, 후자는 해당 업무의 기록과 원문에서 근거를 찾아야 합니다.

현재 샘플에는 「교대 인수인계 기록 기준」과 「경험 지식 검토 기준」이 있습니다. 개발·시연용 질문에도 다음 내용이 포함되어 있습니다.

| 인수인계 질문 | 찾아야 할 근거와 답변의 기준 |
| --- | --- |
| 교대할 때 어떤 내용을 남겨야 할까? | 인수인계 지침에서 관측·조치·결과·미확인 내용·다음 담당자 등 필수 항목 확인 |
| 결과를 아직 모르는 경험을 성공 사례로 남겨도 될까? | 인수인계·검토 기준에서 후속 결과가 없으면 해결 완료로 표시하지 않는다는 규칙 확인 |
| 선임의 경험 메모가 매뉴얼과 다르면 무엇을 따라야 할까? | 검토 기준에서 경험의 적용 한계와 공식 지침의 유효 기간·조건 확인 |

첫 질문에 대한 답변은 다음처럼 구성할 수 있습니다. 아래는 샘플 지침을 바탕으로 작성한 설명용 예시이며 실제 모델의 출력은 아닙니다.

> 교대 기록에는 설비 식별자와 관측 시간, 관측한 현상, 확인한 자료, 시도한 조치, 확인된 결과를 남깁니다. 아직 모르는 내용과 다음 담당자도 함께 기록합니다. 후속 결과가 없으면 해결 완료로 표시하지 않습니다.
>
> 근거: 「교대 인수인계 기록 기준」의 인수인계 항목과 경험의 적용 절.

이 답변에서 확인된 결과와 아직 모르는 내용을 구분하는 것이 핵심입니다. 다음 담당자가 무엇을 이어서 확인해야 하는지 판단하려면, 이전 담당자가 조치를 시도했다는 사실과 그 조치의 결과를 각각 읽을 수 있어야 합니다.

## 현재 인수인계 기준과 과거 기록을 구분하기

인수인계 지침이 개정되었다면 “지금 무엇을 남겨야 해?”에는 현재 승인본을, “지난달에는 어떤 기준으로 인계했어?”에는 당시 유효했던 승인본을 찾아야 합니다. 새 초안은 버전 번호가 높더라도 현재 기준을 대신할 수 없습니다.

과거 인수인계 기록과 현행 지침은 표현이 비슷해 의미 검색에서 함께 발견될 수 있습니다. 그래서 검색을 설계할 때 **질문과 얼마나 비슷한지에 더해, 그 질문의 시점과 적용 대상에 맞는 문서인지**를 판단하도록 했습니다.

문서마다 종류, 승인 상태, 효력 기간, 적용 설비와 버전을 기록할 계획입니다. 질문 기준일을 `D`라고 하면 검색 근거로 사용할 문서는 다음 조건을 만족해야 합니다.

- 초안이 아니며, `approved_at <= D`인 승인 이력이 있습니다.
- 효력 시작일은 포함하고 종료일은 제외합니다. 즉 `effective_from <= D`이고, 종료일이 있다면 `D < effective_to`여야 합니다.
- 선택한 설비에 적용되는 자료이거나 팀 공통 자료입니다.
- 철회되었거나 재검토가 필요한 문서는 제외합니다.

현재 상태가 구버전인 `superseded` 문서도 과거 기준일에는 유효할 수 있습니다. 그래서 `status == approved`만 검사하면 과거 질문에 필요한 근거를 놓치게 됩니다. 같은 문서 묶음인 `family_id` 안에서 유효한 승인본의 기간이 겹치면 충돌로 다룹니다.

현재 샘플은 제조팀의 교대 업무를 가정하므로 적용 대상을 설비 식별자로 구분합니다. 팀 공통 인수인계 지침은 함께 검색하되, 개별 업무 기록이 어느 설비와 작업 조건에 관한 내용인지는 확인해야 합니다.

경험 기록에도 별도의 구분이 필요합니다. “지난번에는 이 항목을 생략하고 인계했다”는 메모를 검토하고 승인해도, 그 경험이 필수 기록 항목을 바꾸는 공식 지침이 되지는 않습니다. 답변에서도 현재 기준과 과거 처리 이력, 경험의 한계를 구분해서 보여주려 합니다.

## 청크와 임베딩으로 검색 후보를 구성하기

기본 접근은 검색한 자료를 생성 모델에 제공하는 RAG입니다. 검색을 통해 외부 지식을 생성 과정에 연결하는 접근은 [Lewis 등의 RAG 논문](https://arxiv.org/abs/2005.11401)에서 확인할 수 있습니다. FieldMemory에서는 다음 흐름을 첫 구현 범위로 잡았습니다.

1. **문서를 등록합니다.** 인수인계 지침·업무 가이드·교대 기록·경험 메모를 가져오고 원본과 추출한 텍스트를 보관합니다.
2. **자료의 상태를 검토합니다.** 문서 종류, 승인 여부, 적용 기간과 대상을 확인합니다.
3. **질문에 맞는 근거를 찾습니다.** 질문 기준일과 설비 조건을 반영하고, 임베딩으로 의미가 가까운 문단을 검색합니다.
4. **근거를 바탕으로 답변합니다.** 최대 20개 후보 중 최대 5개 문단을 생성 모델에 전달하는 구성을 기준으로 삼습니다.
5. **답변 옆에서 원문을 확인합니다.** 각각의 사실 주장에 연결된 문서 버전과 해당 문장을 살펴볼 수 있게 합니다.

예를 들어 “다음 담당자에게 뭘 남겨야 하지?”라는 질문은 문서 제목인 “교대 인수인계 기록 기준”과 표현이 다릅니다. 임베딩 검색에서는 이런 질문을 필수 기록 항목이 적힌 문단과 연결할 수 있는지 확인하려 합니다. “지난 담당자가 무엇을 확인했지?”라는 질문에는 일반 작성 기준뿐 아니라 해당 업무의 실제 기록이 필요합니다.

문서는 모델 토크나이저 기준 **384토큰, 겹침 64토큰**을 출발점으로 나누도록 설계했습니다. 문단 조각인 청크마다 원문 줄 범위를 남겨, 검색 이후에도 해당 위치로 돌아갈 수 있게 합니다. 이 크기는 아직 비교 실험으로 선정한 최적값이 아닙니다.

임베딩 모델 후보는 `intfloat/multilingual-e5-small`입니다. 질문에는 `query: `, 문단에는 `passage: ` 접두사를 붙이고, 정규화한 벡터의 내적으로 순위를 계산할 계획입니다. 비영어권 텍스트에도 같은 접두사를 사용하라는 안내와 정규화 예제는 [공식 모델 카드](https://huggingface.co/intfloat/multilingual-e5-small#usage)에 나와 있습니다. 접두사·특수 토큰까지 포함한 입력 길이도 모델 한도 안에 들어가는지 확인해야 합니다.

벡터의 길이를 1로 정규화하면 두 벡터의 내적은 코사인 유사도와 같습니다. 이 값은 후보의 순서를 정하는 검색 점수로 사용합니다. 예를 들어 점수가 0.8이어도 답변이 맞을 확률이 80%라는 뜻은 아닙니다.

비교군으로는 한국어 문자 n-gram TF-IDF 검색과, 어휘 검색·의미 검색 순위를 합치는 RRF 방식의 결합 검색을 계획했습니다. 모든 방식에 같은 문서 조건을 적용해 검색 방식의 차이를 비교하고, 조건 필터의 효과는 별도 실험으로 확인하려 합니다.

승인 여부나 효력 기간처럼 명확한 조건은 규칙으로 처리하도록 설계했습니다. 생성 모델은 이렇게 찾은 근거를 바탕으로 답을 정리하는 역할을 맡습니다.

색인에는 임베딩 모델 ID와 revision, 청크 규칙 버전, 본문 해시, 자료 전체의 변경 번호인 `corpus_revision`을 기록하도록 했습니다. 본문이나 모델이 바뀌면 같은 검색어라도 결과가 달라질 수 있으므로, 오래된 색인을 식별하고 실험 조건을 재현하는 데 필요한 정보입니다.

## 인용의 형식과 의미를 나누어 검증하기

출처는 답변의 각 사실 주장에 연결할 계획입니다. 어느 버전의 어느 문장으로 해당 주장을 뒷받침했는지 확인할 수 있어야 하기 때문입니다. 데이터 계약에서 정의한 인용의 필드는 다음과 같습니다.

```text
doc_id          문서 버전의 식별자
revision        문서의 개정 번호
start_line      보존한 추출 원문의 시작 줄
end_line        보존한 추출 원문의 끝 줄
quote           해당 범위에서 인용한 원문
content_sha256  본문이 바뀌었는지 확인할 해시
```

먼저 코드로 ID·버전·해시·줄 범위가 맞는지, 인용문이 해당 원문 범위에 실제로 존재하는지 확인하도록 설계했습니다. 그다음에는 그 문장이 답변의 주장을 뒷받침하는지 평가합니다.

예를 들어 가상의 인수인계 메모에 “조치를 시도했지만 후속 결과는 아직 확인하지 못했다”라고 적혀 있는데, 답변이 이를 “이전 담당자가 해결을 완료했다”로 요약하면 의미적으로 틀립니다. 형식 검사를 통과한 인용도 내용 판정이 필요합니다. TypeSafe의 [인용 검증 예제](https://docs.typesafe.ai/cookbooks/citation_check) 역시 원문 문자열의 존재 확인과 주장에 대한 의미 판단을 나누어 다룹니다.

## 답할 수 없는 이유도 구분하기

답변을 만들기 어려운 상황도 처음부터 사용 흐름에 포함했습니다. 사용자가 다음에 무엇을 확인해야 하는지 알 수 있도록 이유를 구분합니다.

| 상황 | 설계한 응답 |
| --- | --- |
| 인수인계 항목을 묻고 유효한 지침이 있음 | 필수 항목과 지침의 원문을 함께 제시 |
| 특정 교대 업무를 묻지만 대상이나 시점이 빠짐 | 어느 업무와 교대 시점을 말하는지 추가로 질문 |
| 같은 시점에 적용되는 승인 지침끼리 충돌함 | 기준 충돌을 알리고 확인 요청 |
| 인계받은 업무의 완료 여부를 묻지만 결과 기록이 없음 | 완료를 뒷받침할 근거가 부족하다고 표시 |

예를 들어 “지난 교대에서 남긴 일은 다 끝났어?”라는 질문에는 어떤 업무와 교대 시점을 말하는지 먼저 확인해야 합니다. 대상이 정해진 뒤에도 조치 기록만 있고 후속 결과가 없다면 완료했다고 단정할 수 없습니다.

다만 지침에 “후속 결과가 없으면 해결 완료로 표시하지 않는다”는 내용이 있다면, 그 기록을 어떻게 인계해야 하는지는 답할 수 있습니다. **업무가 실제로 끝났는지를 확인하는 질문과, 미확인 업무를 어떻게 기록해야 하는지 묻는 질문은 필요한 근거가 다릅니다.** 모든 질문을 같은 이유로 보류하지 않도록 구분하려 합니다.

문서가 바뀌는 상황도 고려했습니다. 근거 문서가 수정·철회·삭제되면 색인과 이전 답변에도 변경이 반영되어야 합니다. 예전 문서를 잘 인용한 답변이라도 지금 질문의 근거로 계속 사용할 수 있는지는 다시 확인해야 합니다.

## 개발 자료와 최종 평가 자료를 분리하기

현재 저장소에는 합성 문서 15개와 개발·시연용 질문 20개가 있습니다. 현행 지침만 넣으면 드러나지 않을 문제를 확인하기 위해 구버전, 미승인 초안, 다른 설비의 기록, 근거가 부족한 질문을 함께 구성했습니다.

각 질문에는 기대하는 응답 상태, 필요한 문서, 근거로 사용하면 안 되는 문서와 만들어내면 안 되는 주장을 정리했습니다. 인수인계 관련 예시에서는 “관측·조치·결과·미확인 내용·다음 담당자를 빠뜨리지 않는가”, “결과를 모르는 경험을 성공 사례로 바꾸지 않는가”를 확인합니다. 이 자료는 구현 중 동작을 점검하고 시연 흐름을 설명하는 데 사용할 계획입니다.

추가 개발 질문 20개와 최종 평가 질문 최소 40개는 별도 자료 묶음으로 준비할 예정입니다. 최종 세트에는 답 가능한 질문 최소 24개와 보류가 필요한 질문 최소 16개를 포함하도록 계획했습니다. 같은 매뉴얼의 다른 버전이 개발·평가 양쪽에 섞이는 것을 막기 위해 문서 `family_id` 단위로 분리합니다.

정답과 금지 주장은 평가기에만 두고 검색 색인이나 생성 모델·Jev 입력에는 넣지 않습니다. 프롬프트와 판단 임계값은 개발 세트에서 정한 뒤 고정합니다. 최종 문항을 본 뒤 설정을 바꾼 실행은 개발 결과로 다시 분류하기로 했습니다.

저장소에는 문서 참조와 샘플 자료의 일관성을 검사하는 스크립트도 있습니다. 이 검사는 자료 사이의 연결을 점검하는 역할입니다. 실제 검색이 필요한 문단을 찾아내는지, 생성 모델이 그 내용을 정확하게 답하는지는 구현 후에 따로 확인해야 합니다.

## 검색과 답변은 각각 어떻게 평가할까

검색이 관련 문단을 찾았더라도 모델이 조건을 잘못 해석할 수 있습니다. 반대로 화면에서 자연스럽게 읽히는 답변이라도 필요한 사실을 빠뜨리거나 근거 없는 내용을 덧붙일 수 있습니다. 그래서 검색 결과와 최종 답변을 나누어 평가할 계획입니다.

검색에서는 필요한 근거가 후보 20개 안에 들어왔는지, 최종적으로 전달한 5개 문단 안에도 남았는지를 확인합니다. 예를 들어 인수인계 필수 항목을 물었을 때 현재 지침의 해당 문단이 후보와 최종 문맥에 포함되는지 살펴봅니다. 후보 회수율@20과 최종 회수율@5를 나누어 보면, 처음 검색할 때 근거를 놓쳤는지 이후 문맥을 고를 때 탈락했는지 구분할 수 있습니다.

답변에서는 필요한 사실을 모두 답했는지, 근거 없는 주장을 추가하지 않았는지, 인용한 문서와 적용 조건이 적절한지를 함께 봅니다. 필요한 지침을 찾았더라도 답변에서 미확인 사항이나 다음 담당자 항목을 빠뜨리면 불완전한 답변입니다. 후속 결과가 없는 업무를 완료로 표현하는 것도 답변 단계의 오류로 다룹니다.

특히 **답변한 질문만 골라 정확도를 계산하지 않도록** 기준을 정했습니다. 답할 수 있는 질문 전체를 분모에 두고, 그중 답변을 보류하거나 API 오류로 실패한 질문도 남깁니다. 어려운 질문을 많이 보류한 결과가 정확도 향상으로 보이는 일을 막기 위해서입니다.

보류가 필요한 질문은 별도로 평가합니다. 근거가 부족한 상황을 올바르게 알아차렸는지와, 충분히 답할 수 있는데도 불필요하게 보류했는지를 함께 볼 예정입니다.

| 지표 | 분자와 분모 |
| --- | --- |
| 엄격한 질의응답 정확도 | 사실·근거·조건을 모두 충족해 답한 질문 수 / 답 가능한 고정 질문 수 |
| 불필요한 보류율 | 답할 수 있는데 보류한 질문 수 / 답 가능한 고정 질문 수 |
| 보류 재현율 | 보류가 필요한 상황에서 올바르게 보류한 질문 수 / 보류 필요 질문 수 |
| 근거 없는 답변 노출률 | 근거 없는 사실을 포함해 답한 질문 수 / 고정 평가 질문 전체 수 |

각 비율에는 분자·분모를 함께 기록하고, 조건 부족·문서 충돌·근거 부족도 구분해 집계할 계획입니다. 실제 LLM 호출 없이 원문만 발췌한 결과는 검색 평가로 기록합니다.

## Jev의 재정렬과 답변 검증을 따로 비교하기

후속 단계에서는 TypeSafe의 Jev를 검색 후보의 재정렬과 주장·근거 검증에 적용하는 실험을 계획했습니다. 자연어 답변은 별도 생성 LLM이 맡고, Jev에는 후보 문단의 관련성이나 주장에 대한 근거 판단을 요청합니다.

| 비교 방식 | 확인할 내용 |
| --- | --- |
| E0 · 기준 | 임베딩 후보 최대 20개 → 상위 5개 → 생성 LLM |
| E1 · 재정렬 | E0와 같은 후보 → Jev 재정렬 → 상위 5개 → 같은 LLM |
| E2 · 검증 | E0에서 저장한 답변 → Jev 주장·인용 검증 |
| E3 · 재정렬과 검증 | E1에서 저장한 답변 → Jev 주장·인용 검증 |

E0와 E1은 같은 후보 캐시를 사용하고, 생성 모델·버전·프롬프트·문맥 예산·샘플링 설정을 고정합니다. E2는 E0의 답변을, E3은 E1의 답변을 그대로 받아 검사합니다. 검증할 때 새로 생성하면 답변의 무작위 차이까지 비교 결과에 섞일 수 있기 때문입니다.

재정렬에서는 질문과 문단을 함께 넣고 “이 문단이 답에 필요한 근거를 제공하는가”를 판단하도록 설계했습니다. TypeSafe의 [재정렬 예제](https://docs.typesafe.ai/cookbooks/rerank_typesafe)는 이런 질문에 `Noul`의 0~1 값을 반환받아 후보 순서를 정합니다. FieldMemory에서는 동점일 때 기존 임베딩 순서를 유지하고, 첫 실험에서는 후보를 임계값으로 제거하지 않을 계획입니다.

이때 Jev는 처음 검색한 후보 밖에서 근거를 추가하지 않습니다. 후보 20개 안에 정답 근거가 없었다면 재정렬만으로 복구할 수 없습니다. 그래서 최종 답변 정확도와 함께 후보 회수율도 확인해야 합니다.

주장 검증에는 해당 주장이 인용한 문맥만 전달하고, `supported`, `unsupported`, `contradicted`, `unclear` 중 하나를 선택하도록 계획했습니다. 통과 기준과 confidence 임계값은 개발 세트에서 정합니다. 최종 성능 판정은 비교 방식의 이름을 가린 상태에서 사람이 수행하며, Jev의 점수를 그 자체의 성능 평가로 사용하지 않습니다.

현재 설계에서 검증 단계는 답변을 통과시키거나 전체 답변을 보류하며 내용을 고치지는 않습니다. 따라서 답 가능한 고정 질문 전체를 분모로 삼는 엄격 정확도에서는 **E2 ≤ E0, E3 ≤ E1**입니다. 틀린 답변을 보류해도 그 질문이 정답으로 바뀌지는 않고, 맞는 답변을 잘못 보류하면 정답 수는 줄기 때문입니다.

재정렬은 정답률 개선을, 검증은 근거 없는 답변의 노출 감소와 정답의 잘못된 보류를 중심으로 평가하려 합니다. 검증 후 답변을 다시 생성하는 방식은 별도 실험으로 분리했습니다.

### 개선률에도 비교 조건을 남기기

같은 질문에서 기준 정답률을 `A0`, 적용 후 정답률을 `A1`이라 할 때, 두 값을 0~1 비율로 두고 다음처럼 계산할 계획입니다.

```text
정확도 변화량(%p) = 100 × (A1 − A0)
상대 개선률(%) = 100 × (A1 − A0) / A0
```

기준 정답률이 0이면 상대 개선률은 계산할 수 없습니다. 성능이 낮아지면 음수 값을 그대로 남깁니다. 질문별 정답·오답 쌍을 보존해 같은 질문 쌍을 재표집하는 paired bootstrap 1,000회로 변화량의 95% 구간을 구하고, 구간에 0이 포함되면 개선을 확정하지 않도록 계획했습니다.

정확도 변화와 함께 응답 시간의 p50·p95, 호출 수·토큰·비용도 기록할 예정입니다. 요청한 방식과 실제 실행한 방식도 남겨, Jev 실패 후 기본 검색으로 복귀한 결과가 Jev 성공 사례로 집계되지 않도록 합니다. Jev 연결과 비교 실험은 아직 수행하지 않았고, 정확도 향상이나 개선률도 측정하지 않았습니다.

## 다음 구현에서 확인할 것

첫 제품은 한 사용자가 한 팀의 자료를 관리하는 로컬 웹앱으로 범위를 잡았습니다. Python·Streamlit·SQLite와 다국어 임베딩을 사용할 계획이며, 답변 모델은 외부 Gemini API 또는 내부 호환 LLM을 선택할 수 있도록 설계했습니다. 내부 LLM 연결이 실패했을 때 외부 API로 자동 전환하지 않는 것도 연결 규칙에 포함했습니다.

다음 목표는 인수인계 지침과 교대 기록을 등록·검토한 뒤, “교대할 때 무엇을 남겨야 하는가”와 “이 기록에서 확인된 결과는 무엇인가”를 질문해 답변과 원문을 함께 확인하는 흐름을 연결하는 것입니다. 이후 질문의 표현과 기준일을 바꿔 보고, 근거 문서를 수정하거나 삭제했을 때 결과가 어떻게 달라지는지 확인하려 합니다.

경험 인터뷰, 외부 서비스의 자동 수집, 조직 단위 권한 관리는 후속 범위로 두었습니다. 우선 문서 한 개가 등록되어 답변의 근거가 되고, 그 문서의 변경이 검색에 반영되는 과정부터 검증할 계획입니다.

다음 개발 기록에서는 기본 검색과 답변을 연결한 뒤, 후보 단계에서 놓친 근거와 생성 단계에서 발생한 오류를 나누어 정리하려 합니다. 실행 당시의 문서·모델·설정과 함께 결과를 남겨, 이후 비교 실험의 출발점으로 삼을 계획입니다.
